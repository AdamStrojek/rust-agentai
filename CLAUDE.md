# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`agentai` is a Rust library for building LLM agents on top of the [`genai`](https://crates.io/crates/genai) crate. genai 0.7 from crates.io takes only text in tool results; `convert.rs` (`messages_into_genai`) works around it (see Tools). Branch `feat/image-generation` holds the switch to the genai fork with native binary parts, to merge once genai releases it. It is pre-1.0 and under heavy development; breaking API changes are acceptable.

Cargo workspace (`resolver = "3"`, members `crates/*`, edition 2021):
- `crates/agentai` – the library.
- `crates/agentai-macros` – proc-macro crate providing `#[toolbox]` (re-exported as `agentai::tool::toolbox`).
- `crates/agentai-core` – shared building blocks: `message` (`Message`, `Part`, `Media`, `ToolOutput`, ...), `prompt` and `history` (`HistoryProcessor` trait, also implemented for `Fn(Vec<Message>) -> Vec<Message>`; `HistoryPruning` replaces media and drops reasoning in finished turns, i.e. up to the last assistant message without tool calls; `Message::without_media`/`without_reasoning`), re-exported by `agentai` under the old paths (genai conversions stay in `agentai/src/convert.rs` as private `FromGenai`/`IntoGenai` traits); `storage` (`MediaRead`, `MediaSave`, `MediaStorage`, `MemoryStorage`; the storage chooses the ID); `tls` (`install_crypto_provider`: installs ring as the process rustls provider with the `rustls-ring` feature; call it before building any `reqwest`/`genai` client, or reqwest panics without aws-lc); and the HTTP client abstraction in `http/mod.rs` (`HttpClient`, `HttpRequest` with `with_bearer_token`, `HttpResponse` with `error_for_status`, in-memory `Multipart` with text, file and JSON parts, `Method::Delete`) with `http/reqwest.rs` (`ReqwestClient`, default `reqwest` feature) so crates can later run on other HTTP stacks (wasm). Keep it runtime-neutral (no clock, randomness or tokio). HTTP and `Media` helpers that provider crates share belong here, not copied into each crate: `mime` (`extension` for a MIME type, with `audio/mpeg`→`mp3`, `audio/ogg`→`opus`, `video/quicktime`→`mov`, `image/svg+xml`→`svg`, else the alphanumeric subtype or `bin`; `from_path` for a name or URL; `with_extension`, which keeps a name's extension only when `from_path` knows it), `base64` (`encode`, `decode`; the only place that uses the `base64` crate), `Media::bytes`, `byte_len`, `extension`, `file_name(stem)` and `to_url` (own URL or a data URL), `HttpResponse::content_type`, and `percent_encode` for a URL path segment or query value. The `test-support` feature adds `mock::MockHttp` (cheap-clone recording `HttpClient`: `new(responses)`, `request(i)`, `request_count()`) with `json_response` and `body_json`; the media crates enable it in `[dev-dependencies]` only. Tests of the MIME table, file names, base64 and data URLs live in core; provider crates test only their own logic and wire format.
- `crates/agentai-image` – image generation on top of `agentai-core`; `agentai` and `schemars` only with the default `toolbox` feature. `provider/mod.rs`: `ImageProvider` (`model`, `generate`, optional `supports_edit`/`edit`), `ImageRequest`, `ImageEditRequest`, `ImageResponse { image: Media, revised_prompt, id }`, `ImageError`, `ImageModel`, `from_model` (`provider::model` prefix or a well-known name) and `list_models(provider)` (both via `ProviderKind::build` from env; the trait method `ImageProvider::list_models` defaults to `Unsupported`); each API is a submodule (`provider/openai.rs`: `/images/generations` JSON, `/images/edits` multipart, lenient parsing for compatible servers, `from_env` reads `OPENAI_API_KEY`/`OPENAI_BASE_URL`, `GET /models` filtered to `gpt-image*`/`dall-e*` only on the official base URL; `send_request`/`parse_response` are shared; `provider/openrouter.rs`: `POST /images` JSON, edits as `input_references` data URLs, `GET /models?output_modalities=image` following `links.next`, `OPENROUTER_API_KEY`/`OPENROUTER_BASE_URL`). Providers are not re-exported at the root; `agentai_core::storage` is re-exported as `agentai_image::storage`, so users need no direct `agentai-core` dependency. `generator.rs`: `ImageGenerator` (defaults for size/quality, optional `MediaSave` that sets `id`; the image name is `ImageRequest::name`/`ImageEditRequest::name` (never sent to the provider, the tools take it as a required `name` argument) or `image`, through `Media::file_name`). `toolbox.rs`: `GenerateImageToolBox` (`generate_image` and `edit_image` always listed, `edit_image` returns `ToolError::Failed` without a storage or an editing provider; both take a required `name`; `ImageToolOutput::Media` or `Metadata` JSON) and `ReadMediaToolBox` (`read_media` by ID), both on `#[toolbox]` (`agentai/macros` is part of the `toolbox` feature). Tests use `agentai_core::mock::MockHttp` and `MemoryStorage`. `mime` and `base64` from core are re-exported for the examples.
- `crates/agentai-audio` – text-to-speech, dialogues, voice cloning and voice design on top of `agentai-core`; `agentai` and `schemars` only with the default `toolbox` feature. A provider has up to three engines, each with its own model: speech (required), dialogue and voice design (optional, no built-in defaults); an engine without a model is off, its call returns `MissingModel` without a request, and `supports_dialogue()`/`supports_voice_design()` mean "that model is set". `provider/mod.rs`: `SpeechProvider` (`generate(&SpeechRequest<'_>)`, optional `create_voice`, `generate_dialogue(&DialogueRequest<'_>)`, `design_voice(&DesignVoiceRequest<'_>)`, `list_voices`, `list_models`, each with its `supports_*`; the model of a call is `request.model()` or the engine's own), `VoiceId = String` (no `Voice` enum; the caller only gives IDs), `VoiceSource` (`Samples` or `SampleId`, from `VoiceSource::samples(..)` or `&VoicePreview`), `VoicePreview`, `SpeechResponse { audio, id, sample_rate, timestamps, model }`, `WordTimestamp`, `AudioModel { id, name, description, speech, dialogue, voice_design }` (one type for the catalogue and API results; `list_models` fills capabilities from the catalogue by `id`), `AudioError` (`MissingModel`, `InvalidRequest`, `Unsupported`, `MissingVoice`, ...). `provider/kind.rs`: `SpeechProviderKind` (`OpenAi`, `ElevenLabs`, `FishAudio`, `Omlx`; `FromStr`/`Display` as `openai`, `elevenlabs`, `fishaudio`, `omlx`; `builder(speech_model)`, `known_models()`: a list in code, empty for oMLX), `speech_provider(impl IntoSpeechProviderKind, speech_model) -> SpeechProviderBuilder` (`with_dialogue_model`, `with_design_model`, `with_voice_store`, `with_api_key`, `with_base_url`, `build() -> Arc<dyn SpeechProvider>`; key and URL fall back to the provider's env vars, `build` sends nothing, an unknown name is `UnknownProvider`, an engine or store the provider lacks is `Unsupported`). Concrete providers stay public with `new(speech_model, api_key, base_url)`, `from_env(speech_model)` and `with_*` only where supported (dialogue: Fish Audio, ElevenLabs; design: Fish Audio, ElevenLabs, oMLX; voice store: Fish Audio, oMLX): `openai` (`/audio/speech`; OpenAI shuts these models down on 2027-01-06), `elevenlabs` (dialogues via `POST /v1/text-to-dialogue` with `inputs: [{text, voice_id}]`, no timestamps; design via `/v1/text-to-voice/design` with the design model, saving a preview needs `voice_description`), `omlx` (no voice library: IDs only from its `VoiceStore`, `Unsupported` without one; design speaks the text once per candidate with the description as `instructions`), `fishaudio` (`POST /v1/tts`, model in the `model` header; every voice ID is looked up in the optional `VoiceStore` first: all found sends only `references` samples as MessagePack, none found only `reference_id` as JSON, a mix is `InvalidRequest` with no request; speech uses the single forms, dialogue the list forms and a text of `<|speaker:i|>` turns built by the provider; `create_voice` makes a voice model with `POST /model`, `list_voices` pages `GET /model?self=true`; timestamps switch to `/v1/tts/stream/with-timestamp`, whose SSE body is parsed whole; design via `/v1/voice-design`; `FISH_API_KEY`/`FISH_BASE_URL`, the key optional with a base URL). `request.rs`: the calls are builders awaited through `IntoFuture` with private fields and getters: `SpeechRequest` (from `generate(text)`: `with_voice`, `with_model`, `with_format`, `with_speed`, `with_language`, `with_instructions`, `with_timestamps`, `with_name`), `DialogueRequest` (from `generate_dialogue(turns)` of `DialogueTurn { voice, text }`; `voices()` are the distinct voices in order of first appearance, `turns()` each turn with its speaker index), `DesignVoiceRequest` (from `design_voice(description)`: `with_text`, `with_count`, `with_model`); `with_model` overrides a configured engine's model for one call and never turns an engine on; `timestamps` a provider lacks is `Unsupported`, `instructions` it lacks is ignored. `generator.rs`: `SpeechGenerator::new(Arc<dyn SpeechProvider>)`/`from_provider(p)` with `with_storage` (an optional `MediaSave` that sets `id`; the name goes through `Media::file_name("speech" | "dialogue")`); no defaults. `toolbox.rs`: `SpeechToolBox` (`generate_speech(text, name, voice, instructions)` reporting `SpeechResponse::model`, `list_voices`; `Metadata` JSON by default or `Media`; `with_voices` is an allowlist, without it the voice the model gives is sent as an ID; no tool reaches dialogues, `create_voice` or `design_voice`). Examples `speech_generator`, `speech_tools` (both read `AGENTAI_SPEECH_PROVIDER` and `AGENTAI_SPEECH_MODEL`), `clone_voice`, `design_voice`, `dialogue` write into `audio/` (gitignored). Tests use `agentai_core::mock::MockHttp` and `MemoryStorage`. `mime` and `base64` from core are re-exported for the examples.
- `crates/agentai-video` – video generation on top of `agentai-core`, with no `agentai`, `schemars` or toolbox: submit, poll, download, and the caller does the polling (no waiting helper, no retries, no timeouts, no sleep or tokio outside dev-dependencies). `provider/mod.rs`: `VideoProvider` (`model`, `submit`, `status`, `download`, optional `supports_cancel`/`cancel`/`list_models`; `status`, `download` and `cancel` need no model, so a provider built with an empty model name follows stored jobs), `VideoRequest` (prompt, duration, resolution, aspect ratio, seed, `VideoInputs`: `None`, `Frames { first, last }` or `References(VideoReferences)`; unset options are not sent, values are not checked client-side), `VideoJob { id, data }` and `JobStatus` (`Queued`, `Running`, `Completed`, `Failed(String)`, `Gone`; serializable, so a job can be stored), `VideoModel` (`None` in a list means the provider does not say), `VideoError`, `from_model` (the `provider::` prefix is required) and `list_models(provider)`. Providers: `comfy_serve` (`ComfyServeVideoProvider`, `/api/v1/videos`, files uploaded as multipart, cancel via `DELETE`, `COMFY_SERVE_BASE_URL` required and `COMFY_SERVE_API_KEY` optional) and `openrouter` (`POST /videos`, frames and image references as URLs or data URLs, no cancel, `OPENROUTER_API_KEY`/`OPENROUTER_BASE_URL`). The two providers share nothing but the types of `provider/mod.rs`: each has its own serde request and reply structs (`#[derive(Serialize)]` bodies, `#[derive(Deserialize)]` replies read with `HttpResponse::json`; an unknown status or a reply without a job `id` is `InvalidResponse`, 404 on status is `Gone`, model entries without `id` are skipped). `mime` from core is re-exported. The example `generate_video` (`AGENTAI_VIDEO_MODEL`, optional `AGENTAI_VIDEO_RESOLUTION` and `AGENTAI_VIDEO_DURATION`) prints the model's capabilities from `list_models`, guesses a first frame's type with `mime::from_path` and writes `video/<job id>.<extension>` (gitignored). Tests use `agentai_core::mock::MockHttp`.

All crates share one version group and are released together by release-plz (`release-plz.toml`) on push to `master`. CHANGELOG.md is generated from commit messages.

## Commands

CI (`.github/workflows/ci.yml`) runs these; keep them passing:

```bash
cargo fmt --check
cargo clippy -- -D warnings
cargo test
```

- Single test: `cargo test -p agentai <test_name>` (e.g. unit tests in `crates/agentai/src/agent/tests.rs`).
- Offline tests only: `cargo test -p agentai --lib` (agent loop against a mock LLM in `agent/tests.rs`, message conversion in `message.rs`, plus `tool/buildin.rs` and `tool/mcp.rs`; the MCP tests need `uvx`, and `test_get_location` calls the live Nominatim API).
- Doc tests only: `cargo test -p agentai --doc`. Every example is included as a runnable doc test (via `src/examples/*.rs`), so plain `cargo test` executes all examples against a live LLM and fails without the env vars below.
- Example: `cargo run --example <name>` (`simple`, `streaming`, `event_listener`, `struct_output`, `tools_custom`, `tools_web`, `tools_mcp`, `tools_deferred`, `tools_deferred_non_streaming`, `vision`, `openrouter`; the last one needs `OPEN_ROUTER_API_KEY` and is only compiled by `cargo test`). `scripts/run-examples.sh` runs them all and writes logs to `logs/`.
- Docs: `cargo doc -p agentai --open` (the `examples` and `structured_output` modules exist only under `#[cfg(doc)]`).

Examples and tests that hit an LLM read only `AGENTAI_MODEL` (default `claude-haiku-5-5`), a genai model name: the agent is built with `Agent::new(model, system)`, so the provider comes from the name and its key and endpoint from genai's environment variables (`ANTHROPIC_API_KEY`; locally `omlx::Qwen3.8-27B-oQ4e-mtp` with `OMLX_ENDPOINT` and `OMLX_API_KEY`). CI uses `claude-haiku-5-5` with the `ANTHROPIC_API_KEY` secret. `tools_web` needs `BRAVE_API_KEY`; `tools_mcp` launches `uvx mcp-server-time`, so `uv` must be installed; `vision` needs a model that accepts images.

## Architecture

**Public types are our own** (no genai types in the public API, `genai` is an implementation detail; the one exception is `Agent::from_client(genai::Client, ..)`, for which genai is re-exported as `agentai::genai`): `message.rs` (`Message { role, parts }`, `Part`, `ToolCall`, `ToolResponse`, `Media`, `ProviderData`; own serde format, lossless `From` conversions to/from `genai::chat::ChatMessage` tested in its unit tests), `agent/model.rs` (`ChatOptions` + `to_genai()`; `extra_headers`/`extra_body` pass provider-specific options through to genai, whose body merge is shallow, `ToolChoice`, `ReasoningEffort`, `Usage`, `StopReason`), `tool::Tool` (converted to `genai::chat::Tool`), `LlmError` (wraps `genai::Error` as a boxed source with `status()`/`is_transient()`). When genai adds something users need, add our own field/variant (`#[non_exhaustive]`) and map it. Naming rule: every setter is `with_*`, getters are bare names.

**Agent** (`crates/agentai/src/agent/mod.rs`): immutable, cheap-to-clone configuration: genai `Client` (private), system prompt (optional: empty means none is sent; `with_system`), default model (`with_model`; `None` only for `Agent::default()`, a run without any model fails with `MissingModel`) and toolbox (`with_toolbox`, stored as `Arc<dyn ToolBox>`), `max_iterations` (default `DEFAULT_MAX_ITERATIONS` = 5) and `ChatOptions` (empty by default), plus `history_processors` (`with_history_processor`, run in order in `run_loop` before every model call on history + this run's messages; only the request changes, never the caller's history or `new_messages`; an error is `AgentError::History`). The library never sets model parameters (temperature, max tokens, ...) of its own: only the user does, and handles the provider errors for parameters a model does not accept. It does not keep a conversation. Constructors: `Agent::new(model, system) -> Result<_, AgentError>` (`ClientInit`; provider from the model name or a `provider::` prefix, keys from genai's env vars), `Agent::from_client(genai::Client, model, system)` for custom endpoints, keys and HTTP settings, and `Agent::default()` (no model, no system prompt; panics if the client cannot be built). Do not add provider-specific constructors: genai's model namespaces and `from_client` cover them. `anyhow` is a dev-dependency only; the library uses `thiserror` enums.

**Runs** (`request.rs`, `stream.rs`): `Agent::run::<D>(prompt)` (`prompt: impl IntoPrompt`, see `prompt.rs`: `&str`/`String` via a blanket impl over `Into<String>`, `Media`, or a `Prompt` of text and media parts that becomes the first user message) and `Agent::run_stream::<D>(prompt)` return the same `AgentRequest<'a, D, M>` builder (`with_history(&[Message])`, `with_model/with_toolbox/with_max_iterations/with_chat_options`, `with_options(RunOptions)`); the mode marker `M` (`Complete`/`Streaming`) only selects the `IntoFuture` impl. Awaiting `Complete` gives `AgentResult<D>` (`answer`, `new_messages`, summed `usage`, `stop_reason`, `reasoning_content`, `iterations`); awaiting `Streaming` validates the config and gives `AgentStream<D>` (`Send + 'static`) of `AgentEvent`s (`TextDelta`, `ReasoningDelta`, `ToolCall`, `ToolResult`, `Finished(AgentResult)`); `AgentStream::listen`/`listen_async` pass every event to an `EventListener`/`AsyncEventListener` (`listener.rs`; listeners get a borrowed, answer-type-free `RunEvent` so they stay dyn-compatible and can later be attached to `Agent`, for example for a GUI). `listener::Printer` is the ready-made listener, configured on itself with `with_*`; `print_to` (`std::io::Write`), `print_to_async` (`futures::io::AsyncWrite`) and `print_to_tokio` (feature `tokio`, via `Printer::tokio`) are shortcuts that build a default `Printer`. The stream itself takes no printing options. Keep the core runtime-neutral (the goal is to build for wasm later): tokio-specific code goes behind the `tokio` feature. The caller owns the history: it is only read, and `AgentResult::new_messages` holds just this run's messages. The system prompt is sent with `ChatRequest::with_system` and never stored in the history.

**Agent loop** (`core.rs`, `run_loop`): one `async_stream::try_stream!` used by both modes (`streaming: bool`; awaiting `run` drains it with `finish`). The response format is resolved up front in `AgentRequest::resolve` (if `D != String`, a schemars JSON schema with `$schema`/`title` stripped, since Gemini rejects them). The loop runs up to `max_iterations`, each time sending system prompt + history + this run's messages (converted to genai) + toolbox definitions. Non-streaming uses `exec_chat`; streaming uses `exec_chat_stream` with all `capture_*` options on, yields deltas and rebuilds the step from `StreamEnd`. If the reply has tool calls, `into_assistant_message_for_tool_use()` is stored (converted to `Message`) and every call gets a `ToolResponse`; recoverable tool errors (`ToolError::is_recoverable()`: `NotFound`, `InvalidArguments`, `Failed`), and calls made without a toolbox, are sent back to the LLM as text, while a fatal tool error (`Configuration`, `Fatal`) stops the run with `AgentError::Tool`. Otherwise all text parts are joined and deserialized into `D` (a `String` result is JSON-quoted first so that `serde_json::from_str` works). Errors: `MissingModel`, `MaxTokens { raw }` (checked right after every model call, before tools run), `MaxIterationsReached`, `InvalidAnswer { raw, .. }`, `Llm(LlmError)`; `AgentError::is_transient()` flags retryable provider failures. Unit tests in `agent/tests.rs` use a mock OpenAI-compatible server (JSON and SSE replies).

**Tools** (`tool/mod.rs`): the `ToolBox` trait (`#[async_trait]`, `Send + Sync`) has `tools_definitions()` and `call_tool(&ToolCall) -> ToolResult<ToolOutput>` (the whole call, so tools see `id`, `name`, `arguments`) (`ToolResult<T = String>`; `ToolOutput { parts }` holds `Part::Text`/`Part::Media`, so tools can return images; `ToolResponse.content` is `Vec<Part>` and still deserializes the old string format; genai 0.7 tool results hold only text, so `convert::messages_into_genai` sends the tool text in the tool message and the media of a step's tool results in one `user` message right after its tool messages, each call's media after an "Attachments returned by tool call <id> (<name>):" text part, for every provider; this matches what the genai fork does for Chat Completions, and the fork sends it natively for the other adapters; the history keeps the media in the `ToolResponse`). Tools never return structured output: converting data to text (for example JSON) is the tool's job, and the docs say so; do not add a JSON part to `ToolOutput`. `ToolBoxSet` combines several toolboxes and dispatches to the first one that does not return `ToolError::NotFound`, so that variant is the "try the next toolbox" signal. Feature-gated implementations: `buildin` (`tools-buildin`), `web` (`tools-web`, Brave search plus URL fetch), and `mcp` (`mcp-client`, `McpToolBox` on the official `rmcp` SDK: stdio via `new`, Streamable HTTP via `new_http`; unknown tool names return `NotFound`, server-reported tool errors become `ToolError::Failed`, a broken transport is `ToolError::Fatal`). All features are on by default.

**TLS features** (same names in `agentai`, `agentai-core`, `agentai-image`, `agentai-audio`, `agentai-video`): `rustls-ring` (default), `rustls-aws-lc`, `native-tls` (`compile_error!` with a `rustls-*` one), `system-proxy` (default). genai, reqwest and rmcp are pulled in without their default TLS (rmcp without its `reqwest` feature), so nothing enables `reqwest/rustls` and aws-lc stays out of the default build; keep it that way when adding dependencies (`cargo tree -i aws-lc-rs` must find nothing).

**`#[toolbox]` macro** (`agentai-macros/src/lib.rs`): applied to an `impl` block. Every method marked `#[tool]` (or `#[tool(name = "...")]`) must take `&self` and return `ToolResult<T>` with `T: Into<ToolOutput>` (text or `ToolOutput`; the generated `call_tool` maps the result with `Into::into`). A parameter of type `&ToolCall` (any path ending in `ToolCall`) is filled with the current call and left out of the params struct and schema. For each tool the macro generates a hidden `<Method>Params` struct deriving serde and `JsonSchema` (draft 2020-12, no meta-schema), with parameter doc comments carried over as field descriptions. It then generates a `ToolBox` impl whose `call_tool(&self, call: &::agentai::ToolCall)` uses a `match` on `call.name`; before deserializing, `agentai::tool::parse_json_string_arguments` (schema cached in a `OnceLock`) replaces string arguments whose schema allows an array/object but no string with the parsed JSON, when it parses as an allowed type (`parse_json_strings = <bool>` on `#[toolbox]` or `#[tool]`, default on, the tool's option wins); argument deserialization errors become `ToolError::InvalidArguments` and errors returned by the method pass through unchanged. The generated code refers to `Tool`, `ToolBox`, `ToolError`, `serde`, `serde_json`, `schemars`, and `async_trait` by unqualified or crate paths, and to `::agentai::tool::ToolOutput` (inside `agentai` this works through `extern crate self as agentai`), so the caller's crate must have them in scope or as dependencies.

## Tests

Write a test only when it can catch a real bug in `agentai`. Before adding one, ask: which plausible change to our code would make it fail? If the answer is "none" or "a change in another crate", do not write it.

Useful tests:
- Our own logic with real branches or edge cases, for example `Media::image_url` guessing the MIME type (query strings, letter case, fallback), the agent loop's handling of tool errors and iteration limits.
- How `agentai` works together with other libraries and providers: what actually goes over the wire (request bodies checked on the mock LLM server in `agent/tests.rs`), what we read back from replies, lossless conversions between our types and genai's.
- A regression test for a bug that actually happened, at the level where it happened (for example the request body), not just the one-liner that fixed it.

Pointless tests, do not write them:
- Testing the behaviour of other libraries instead of our cooperation with them: that `base64` encodes, that serde round-trips a derive, that `Vec::push` keeps order, that a blanket `impl` converts a `&str`.
- Tests the compiler already guarantees, or that repeat a trivial one-line impl or a builder setter.
- Tests that check one field to "guard" a broad rule (for example "no temperature is sent" for "the library sets no model parameters"): they pass while the rule is broken.
- Tests of a constant's value or of a renamed old test kept only so that something still passes.

When a fix touches a provider's format that the unit tests cannot reach (for example Anthropic, while the mock speaks OpenAI), rely on the doc tests in CI instead of a unit test of our own conversion function.

## Documentation conventions

- Describe changes from the library user's point of view: what they can now do, or must do differently, when building agents. This applies to "What's New", changelog notes, PR descriptions and `llms*.txt`. Order items by how much they change the user's code or what they can build. Put internal work last and keep it short, for example dependency upgrades, refactors and CI. For a dependency upgrade, name the user-visible effect (for example "tool calls are no longer lost"), not just the version.
- "What's New" entries (in `lib.rs`, mirrored in the README) use the heading format `#### X.Y.Z - <highlights>`. If the release has breaking changes, end the entry with a short **Breaking changes** paragraph that names them and tells the user to read the CHANGELOG before upgrading.
- `MIGRATION.md` in the repo root is the migration guide. Every release with breaking changes adds a section at the top, `## X.Y.Z → A.B.C (YYYY-MM-DD)` from the previous release to the new one (one jump only, never from older releases), with the date of the new release and before/after code for each change users must make. Mention only what user code actually touches. The release's CHANGELOG entry and the "What's New" Breaking changes paragraph link to its section.
- `README.md` between `<!-- cargo-rdme start/end -->` is generated from the crate docs in `crates/agentai/src/lib.rs` by cargo-rdme. Edit `lib.rs` and then regenerate; do not edit that section by hand.
- Feature-flag docs come from the `## ` / `#!` comments in `crates/agentai/Cargo.toml` (via `document-features`).
- `llms.txt` (index, llmstxt.org format) and `llms-full.txt` (complete usage guide) in the repo root are hand-written summaries of the public API for LLMs. When a change touches the public API, feature flags, tool names or run behaviour, update both files and the version they name.
- Each example in `crates/agentai/examples/X.rs` has a matching docs-only module `crates/agentai/src/examples/X.rs` that `include_str!`s it. When you add an example, add that module and register it in `src/examples/mod.rs`.
